# 02 · 上下文从哪来：消息树与现场组装

> 本篇回答：**上下文从哪来？**
> 读完你能：理解消息模型与消息级树，明白“上下文不是状态，是每次调用
> 前现场组装的视图；历史可手术”，并会看上下文预算。

## 2.1 Message：一切信息的统一表示

用户输入、LLM 响应、工具结果、外部事件、子 Agent 回执——全部统一表示为
`Message`。它是对象层模型：**消息没有 `role` 属性**，`kind` 描述“这条
消息来自谁”，kind → 各家 API role 的映射是 Provider adapter 的职责
（Anthropic `assistant`、OpenAI `assistant`、Gemini `model`……）。

七值 `MessageKind`：

| kind | 来自谁 | 排队? |
|---|---|---|
| `USER` | 用户 | 进队列 |
| `PROVIDER` | 模型响应（含多模态输出） | **永不进队列**（回合内产生） |
| `TOOL` | 工具执行结果 | 不入队（回合内直接挂树） |
| `SYSTEM` | 框架/Composable 的上下文注入 | 双通道（见 §2.4） |
| `PEER` | 另一个 Agent 有意图地发送 | 进队列 |
| `EVENT` | 外部事件或扩展交付内容（如 cron、异步工具终值、Skill 正文） | 进队列 |
| `SUBAGENT` | 子 Agent 返回结果 | 进队列 |

`content` 是 ContentBlock 列表，不同 type 可交错：`TextBlock` /
`ThinkingBlock`（带 Provider 签名）/ `ToolCallBlock` / `StructBlock`
（对程序是结构、对 LLM 是 dumps 文本）/ 媒体块（`ImageBlock` 等，一律
base64 内联，`data` 是权威表示）。

两条铁律：

- **配对锚**：PROVIDER 消息里 `ToolCallBlock.id` 与后续 TOOL 消息的
  `tool_call_id` 严格 1:1 成对；`Message.__post_init__` 双向强制
  `kind=TOOL ⟺ 配对字段非 None`——孤儿结果消灭在构造点。
- **kind 无行为含义**：不存在“纯系统消息不触发 LLM”之类的短路；kind
  只决定 adapter 的呈现映射。

## 2.2 消息级树：历史是一棵可手术的森林

消息不只排队，还**挂树**。每个 Agent 持有一棵消息级树：

- 节点 = 消息（`id` + `parent_id` 链），`parent_id=None` 是根标记——
  **允许多个根**（森林模型），不设虚拟根；
- `current_head_id` 是游标：新消息链到它并随即前移；上下文组装沿
  `parent_id` 从 head 上溯到根；
- **`fork(msg_id)` 只切游标**，从不创建节点——同一份历史可以同时存在
  多条分支（探索 A/B 方向），旧分支完整保留。

落盘是记录流形态的 `tree.jsonl`（一行一条记录，追加为主、定期清洗重写）。三个持久化标记各一句：

- `turn_end`：本条 PROVIDER 消息落盘时回合随之关闭——恢复时据此定位
  完整回合边界；
- `partial`：流式被中断时，已累积内容**保留落盘**（不丢弃）；
- `synthetic`：恢复时发现孤立 tool_call（结果消息缺失），合成一条
  确定性 id 的占位 TOOL 消息封闭配对——上下文永远成对，adapter 不需要
  也不应该自行修补。

**历史手术**：修改历史走 `agent.chain`（`MessageChain`）五 op——
`insert` / `branch` / `remove` / `update` / `reparent`，最小完备集。
每个 op = 改内存权威链 + 同步 append 一条变更行（tombstone/move/update），
物理重写延迟到压缩期。两个容易误用的点：

- `insert` 在分叉点会把多个子分支**合并**到新消息之下；只想加平行分支
  用 `branch`（`branch(None, msg)` 是唯一的开新根入口——上下文压缩换链
  即此场景）；
- `remove` 不级联子树：直接子自动重挂到被删消息的亲节点，链保持连续。

`turn_end` 之后的“半截 turn”（崩溃撕裂）恢复后照常进入上下文——
它们是已产生的完整历史，不截断、不续跑。

## 2.3 Context：Provider 的唯一输入

每次调模型前，Agent 现场组装一个 `Context`——**三个正交字段，不是扁平
消息列表**：

```python
Context(
    system_prompt=[PromptSegment, ...],   # 分层 prompt 段（保留 cache 标记）
    tools=[ToolDefinition, ...],          # 当前启用的工具声明
    messages=[Message, ...],              # 根 → head 的消息路径
)
```

三字段结构让 adapter 的映射是机械逐字段转换。关键语义：

- **现场求值、零缓存**：每次组装重新求值所有 Parsable、重新收集消息路径、
  重新生成工具定义。这是功能正确性前提（环境变量、实例属性永远最新），
  不是性能选择；
- **无隐式附加**：`finish` / `subagent-invoke` 等内置工具必须由用户显式
  声明（`tools:` / `add_tool`）才进 `Context.tools`——注册 ≠ 可见；
- 组装产物经 `before_provider_gen` 钩子后才发给 Provider——handler 可
  整体改写三个字段（但不推荐改 `messages`：改动不落盘，下次组装即丢）。

## 2.4 prompt_blocks：system prompt 的分层注册

system prompt 不是一段文本，而是**按注册顺序拼接的分层片段**——框架骨架、
插件、应用各自注册、各自管理，互不感知：

```python
async def setup(self):
    self.mode = "讲解模式"
    self.prompt_blocks.append(
        "session-info",
        Parsable("本次会话由 {{ node_id }} 承载，模式为 {{ mode }}。"),
        cache="dynamic", by="demo", tags=["demo"],
    )
```

要点：

- `prompt_blocks[0]` 是框架注入的惰性引用块（内容是
  `{{ self.system_prompt }}` 模板，`by="core"`）——`setup()` 里改类属性
  `system_prompt`，下次组装自动反映；**不得删除它**（system prompt 会
  消失，框架不兜底）；
- `cache`（static/dynamic/session）只是给 adapter 的**意图标记**：框架
  本地不读、不缓存；
- 管理操作：`disable_by_tag` / `enable_by_tag` / `remove_by_owner` 等——
  模式切换的正规手法（注册两套块，按 tag 启停）；
- 动态内容放进 Parsable 模板引用（如 `{{ current_mode }}`），随每次组装
  现场求值拿到最新值；高频值（当前时间）走消息通道（`before_turn` 的
  `pending_messages` 附加式注入）——prompt 内容稳定才能命中 provider
  前缀缓存。

`SYSTEM` 因此有**双通道**：prompt_blocks 通道（每轮进 system_prompt，不
触发新回合）与消息队列通道（进历史、触发新回合）。

## 2.5 上下文预算：锚点实测 + 尾部估算

`estimate_context_tokens()` 回答“现在把上下文发给 LLM 大约多大”：沿
head 上溯找最近一条带实测用量的 PROVIDER 消息作**锚点**，锚点覆盖部分用
实测（`measured`），之后的新内容用字符启发式估算（`estimated`）。
`usage_ratio` 不 clamp——>1.0 是合法的溢出信号；模型未声明
`context_window` 时为 `None`。

估算是 Python 侧的观测 API（REPL 的快速体检用 `/status` / `/snapshot`）。
下面的 Workshop 示例完整列出运行文件、提示词、输入和两轮交互结果；估算值
是一次会话的记录值，受语言、模型用量和消息历史影响：

```python
est = agent.estimate_context_tokens()
# tokens=2349 measured=2065 estimated=284 ratio=None
#   measured=2065：恢复的历史中最近一条 PROVIDER 消息带来的实测锚点
#   estimated=284：锚点之后的尾部消息估算；模型未声明 context_window → ratio=None
```

阈值判断与压缩是**策略**，框架只给观测值。压缩可用的机制底座是：摘要作为
`branch(None, msg)` 的新根开新链，再 `fork()` 切游标；旧树完整保留，随时
可切回。

## 2.6 完整示例：两轮交互后的上下文估算

main.py：

~~~python
"""入口：launch 导入本文件并等待 main() 返回 Runtime。"""

from flowing import Runtime


async def main() -> Runtime:
    runtime = Runtime(persist_dir="@/.flowing")
    # runtime.set_providers("@/providers.yaml")
    # runtime.set_models("@/models.yaml")
    runtime.set_model_tags("@/model-tags.yaml")
    await runtime.mount("@/root.fya", agent_id="agent-main")
    return runtime
~~~

实际日期和模型文本可能不同。下面的 inspect_context.py 可在这两轮对话结束后读取上下文估算：

inspect_context.py：

~~~python
import asyncio

from flowing import launch


async def main():
    runtime = await launch(".")
    try:
        agent = await runtime.get_agent("agent-main")
        if agent is None:
            raise RuntimeError("agent-main is not available")
        estimate = agent.estimate_context_tokens()
        print(
            f"tokens={estimate.tokens} measured={estimate.measured} "
            f"estimated={estimate.estimated} ratio={estimate.usage_ratio}"
        )
    finally:
        await runtime.shutdown()


asyncio.run(main())
~~~

在同一工作目录运行 python inspect_context.py。一次记录的结果为：

~~~text
tokens=2349 measured=2065 estimated=284 ratio=None
~~~

measured 是恢复历史中最近一条带实测用量的 Provider 消息提供的锚点；estimated 是锚点之后新内容的估算值。实际数值会随语言、模型回复和消息路径变化；模型未声明 context_window 时，ratio 为 None。

## 2.7 小结

1. 信息统一表示为 `Message`；kind 描述来源，role 映射归 adapter；
2. 历史是消息级树（森林与 head 游标）；`fork()` 切换视角，五种操作修改历史；
3. `Context` 有三个正交字段，并在每次调用前**现场组装**；惰性求值是正确性前提；
4. system prompt 分层注册；预算观测与压缩策略分离。
