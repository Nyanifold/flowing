# 04 · 装配与控制：钩子、注入与运行环境

> 本篇回答：**怎么装配与控制？**
> 读完你能：在正确的时点装配 Agent，用钩子做拦截与观察，用注入与状态袋
> 管理数据，理解取消语义，并把系统嵌入真实运行环境。
> 本篇遵循原则：**机制在核心，策略在扩展**，装配与运行控制也应遵循这一边界。

## 4.1 装配时点：setup() 与两对生命周期钩子

第 01 篇给了创建管线的骨架，这里钉死时点规则：

- `setup()` 只做**状态赋值、钩子注册、inject 读取、Composable 调用**；
  网络/重 IO 放工具里。create 与 recover 两条管线各自在一个新实例上执行
  同一份 `setup()`——每个实例恰好一次，装配结果一致；
- 两对钩子完全独立：`before_create`/`after_create` 只在创建管线触发，
  `before_recover`/`after_recover` 只在恢复管线触发。“只应在创建时做”
  的逻辑放前者（注意它只能经类上 `@on('before_create')` 声明——此刻
  `setup()` 尚未运行）；
- `setup()` 后框架做 PENDING 检查：必填字段（如 `system_prompt`）未兑现
  即创建失败；`@on` 指向未声明钩子点同样失败——fail fast，不留半装配
  实例；
- `**kwargs` 持久化进 `meta.json` 并随恢复透传——**必须 JSON 可序列化**，
  它是身份的一部分；宿主机对象（连接池等）走 `provide` / Resource。

## 4.2 钩子系统：实例级、可改写、可阻断

每个 Agent 持有独立的钩子注册表（`agent.hooks`），全部钩子只对当前实例
生效。handler 统一签名 `(agent, value)`，三种出口：返回（可改写的）
value / `raise Intercepted` 硬阻断 / 普通异常上抛。注册两种写法：

```python
from flowing import on

class OrderAgent(Agent):
    @on("before_tool_call")              # 类上声明（__init__ 即注册）
    async def _guard(self, tool_call):
        # 命令内容检查：含 rm -rf 即阻断
        if tool_call.name == "bash" and "rm -rf" in tool_call.args["command"]:
            raise Intercepted("命令包含 rm -rf，已阻断")   # → ToolResult.blocked
        return tool_call

    async def setup(self):
        self.hooks.after_turn(self._audit)   # setup 内注册（实例级）

    async def _audit(self, agent, turn):
        log.info("turn done: aborted=%s msgs=%d", turn.aborted, len(turn.message_ids))
        return turn
```

三种出口在 `_guard` 里俱全：返回（可改写的）`tool_call` 是放行（顺手
改参数就是改写，比如把危险命令改写成安全形式）；`raise Intercepted` 是
拒绝——LLM 收到 `blocked` 结果与原因，可以向用户解释“该操作被拦截”
而非“执行失败”，典型应对是换一种安全写法重试；普通异常直接上抛，没有
兜底钩子接住它。决策权始终在你的 handler 里，框架只提供拦截机制。

**从拦截到审批**：`before_tool_call` 天然就是人工审批闸——handler 是
`async` 的，可以在里面 `await` 一次外部确认再决定三出口（handler 内
`await` 普通协程是安全的；死锁禁令只针对 `await query()`）。审批通道
首先只是**自己的一个方法**：钩子是机制，`confirm` 是你的策略——它可以
自由调用外部函数（弹窗、IM 询问、HTTP 回调……由你的应用形态决定）：

```python
class OrderAgent(Agent):
    @on("before_tool_call")
    async def _approval(self, tool_call):
        if tool_call.name == "bash" and "rm -rf" in tool_call.args["command"]:
            if not await self.confirm(tool_call.args["command"]):
                raise Intercepted("用户拒绝了该命令")
        return tool_call

    async def confirm(self, action: str) -> bool:
        # 审批通道：你的应用形态——弹窗、IM 机器人、WebSocket 询问……
        return await ask_user(action)
```

要点：框架给的是“可等待、可阻断的钩子点”这一机制；“问谁、怎么问、
问完怎么办”是策略，起点就是 Agent 上的一个普通方法。

钩子点按族速览如下：

| 族 | 代表钩子点 | 典型用途 |
|---|---|---|
| 生命周期 | `before_create` / `after_create` / `before_recover` / `after_recover` / `before_destroy` / `after_destroy` | 装配补充、派生结构重建 |
| 回合 | `before_turn`（附加式注入）/ `on_turn_abort` / `after_turn`（唯一全路径收尾观察点） | 提醒注入、计数、审计 |
| 消息 | `on_enqueue`（可拒绝）/ `on_dequeue`（可变换批次）/ `on_turn_append` | 内容审核、流式上屏 |
| 模型 | `before_provider_gen`（可改写 Context）/ `after_provider_gen` / `on_provider_delta` / `on_provider_error` | 上下文改写、流式 UI、错误处置（观察/换模型/重试） |
| 工具 | `before_tool_call`（拦截闸）/ `on_tool_yields`（产物级：同步/收据/分段/终值，带元信息）/ `after_tool_call` | 拦截与审批、内容扫描、结果改写、缓存短路 |
| 子 Agent | `on_subagent_invoke` / `on_subagent_returns` | 唤起拦截、结果改写 |
| 其它 | `on_fork` / `before_cancel` / `after_cancel` | 分支守卫、取消守卫 |

三个易错点：`Intercepted` 是**有意硬阻断**（直挂 `Exception`，不入异常
层次）——`before_tool_call` 拦截 → `blocked`（工具未执行），
`after_tool_call` 拦截 → `blocked`（结果已产出但被丢弃）；`after_turn`
handler 异常不会楔死 Agent（等待者照常拿到结果）；`watch(name, handler)`
是纯观察的赋值事件通道（fire-and-forget），不是钩子点。工具侧两个
结果钩子的分工：`on_tool_yields` 是产物级——同步结果、后台收据、
每个分段与终值逐份触发，value 带 `name` / `tool_call_id` /
`production` 元信息，是内容扫描与产物改写的落点；`after_tool_call`
是调用级——每次 `tool_call()` 调用一份（含 shortcut 路径），管结果
处置。

## 4.3 provide-inject 与状态袋：两条数据通道

**provide/inject** 管“跨层共享的运行期值”：`provide(key, value)` 注册，
`inject(key)` 沿 `_parent_id` 链先近后远上溯（终点 Runtime），找不到抛
`MissingProvideError`。规则：

- 同 key 覆盖写、实时查找——运行时切换配置（如 locale）的正规通道；
- **敏感信息边界**：注入值不进消息流、不进 LLM 上下文、不落盘；但沿链对
  后代可见——凭证应在**深层节点** provide，收窄可见范围；
- 影响装配的值在 `mount()` 前 provide；跨 Agent 的重资源（连接池、索引）
  走 `register_resource`（树外直引，不走注入链）。

**状态袋**管“要持久化的业务状态”：

```python
async def setup(self):
    self.state.register("visit_count", 0)   # 缺省即写、写透落盘

# 读写（写透不触发 watch）
self.state["visit_count"] = self.state["visit_count"] + 1
```

`agent.state` 是默认袋（`state.jsonl`），`register_state("name")` 开独立
命名袋；Runtime 侧另有全局袋（`core` 名录 / `default`）。恢复时**已持久
值优先**——setup 中的 register 缺省不会覆盖持久值。

本例把 §4.1–4.3 中的 prompt 分层、工具钩子与状态袋组合到同一个 Agent 中。准备 Python 3.13 或更高版本、已安装的 Flowing，以及由环境变量提供的 DeepSeek API 凭证。以下列出完整运行文件、提示词、配置、输入与两轮交互输出；{{env.DEEPSEEK_API_KEY}} 仅是环境变量占位符。

~~~python
"""入口：launch 导入本文件并等待 main() 返回 Runtime。"""

from flowing import Runtime


async def main(resume: str | None = None) -> Runtime:
    runtime = Runtime(persist_dir="@/.flowing")
    # runtime.set_providers("@/providers.yaml")
    # runtime.set_models("@/models.yaml")
    runtime.set_model_tags("@/model-tags.yaml")
    if resume is not None:
        await runtime.recover_agent(resume)
    else:
        await runtime.mount("@/root.fya", agent_id="agent-main")
    return runtime
~~~

## 4.4 控制流：协作式取消与错误决策

**取消是协作式的**：`cancel()` 置位信号（全部执行条目 + 当前回合），
执行体在检查点自行决定立即停止 / 忽略并完成 / 收尾后返回部分结果——
cancel 是正常终止不是错误。粒度族：`abort_turn()`（只终止当前回合）<
`cancel_by_tag()` / `cancel_children()` < `cancel()`（整个 Agent）；
`stop()` 是留给子类覆写的强制式入口（默认等价 cancel）。`pause()` /
`resume()` 挂起工作循环检查点（含 `_recursive` 子树版本）。
`before_cancel` 里 `raise Intercepted` 可**阻止取消**（支付已提交等不可
中断场景）。

**Provider 错误**一律经 `on_provider_error` 钩子分发（含 token 超限的
`ContextLengthError`——原样重发必然重现，但压缩历史、换大窗模型、仅
观察都是 handler 的合法处置）。这个钩子是多用途的通用通道：handler 可以只做观察（记录、告警、上报监控），可以改换模型
（`self.model` / `model_tag`），可以 `abort_turn()` 主动终止回合，也
可以在退避之后写 `can_continue=True` 让回合内重试——**做不做、做哪
种，都是 handler 内部的逻辑**。框架只读一个字段：
`can_continue=False`（默认）回合以 `error` 收尾（Agent 存活），`True`
则重新发起 `provider_gen`。内置的 `use_retry` 只是挂在这条通道上的一
个可选 handler；不启用时通道照常分发，只是没有人改写决策字段。

**策略外置**：重试、压缩、拦截规则都不在核心——内置 Composable
`use_retry(agent)` / `use_compact(agent)` / `use_auto_compact(agent)` /
`use_system_reminder(agent)` / `use_prompt_until(agent)`
就是示范：通过 ``use_xxx(agent, ...)`` 在 Agent 上注入策略。常见做法是
declare 钩子点并注册 handler；函数也可挂载 Agent 属性、登记状态或执行
其他应用层逻辑。临时状态可放闭包变量或 Agent 属性中：把状态放在该次
调用创建的闭包中，可避免与 Agent 属性名冲突，但外部无法通过 Agent 直接
访问；Agent 属性便于外部读取和管理，但需避免命名冲突。需要持久化的状态可通过 Flowing 内置的
``agent.state.register()`` 登记，也可由应用自行维护持久化与恢复；闭包
变量和普通 Agent 属性本身不提供持久化能力。
同一个 Composable 可使用不同参数多次调用；框架不对调用自动去重，具体
组合语义由函数实现决定。挂载 handler 时可按 ``by`` 归组，以便需要时
整组移除。

## 4.5 运行环境：main() 策略、配置链与嵌入

**`main()` 是策略层**：新建/恢复分支、固定 `agent_id` 幂等 mount、插件
`install`（须在首个 mount 前，迟装对已建 Agent 无效）、根级 provide/
Resource 注册——都在这几个函数里。恢复后运维：亲代链自动向上恢复、子代
惰性现场恢复，`archive_orphans()` 清理崩溃遗留的孤儿。

**配置链**（与模型三文件正交）：框架默认值 < 项目级 `@/config.yaml` <
用户级 `$FLOWING_CONFIG_HOME/config.yaml`，运行期 `set_config` 覆盖层
最优先；`FLOWING_*` 环境变量由各自消费点直读（路径/开关类）。

**嵌入宿主应用**（CLI 之外的正规形态）：宿主持有 `launch` 返回的
Runtime——输入走 `query`/`message`/`steer`，**输出走钩子订阅**
（`on_provider_delta` 流式上屏、`after_turn` 完成通知、
`before_tool_call` 做调用拦截），配置经 `set_config`/`provide` 对接宿主
体系。三条边界：`@` 上下文 per-Task 隔离，多 Runtime 共存（强隔离用
子进程）；launch 返回后模块级 `resolve()` 不可用，用
`runtime.resolve_path`；**`shutdown()` 责任转移给宿主**（write-behind
需要排空，不 shutdown 直接退进程丢尾部记录）。

**观测**：`runtime.snapshot()` / `agent.snapshot()` 是只读一致性快照
（拉取通道；推送靠钩子），全部字段 JSON 可序列化，敏感值（provide 内容）
绝不进入。

## 4.6 小结

1. 装配时点：`setup()` 轻量、两对生命周期钩子独立、kwargs 即身份；
2. 钩子是唯一的扩展总线：实例级、可改写、`Intercepted` 硬阻断；
3. inject 管运行期共享、状态袋管持久化、Resource 管重资源；
4. 取消是协作式的，Provider 错误有决策点；**重试、压缩与拦截规则属于
   Composable 和插件中的策略**，编写扩展时也应遵循这一原则；
5. `main()` 是策略层；嵌入 = 持有 Runtime + 钩子订阅 + 负责 shutdown。
