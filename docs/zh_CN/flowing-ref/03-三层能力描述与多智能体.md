# 03 · 能力从哪来：三层能力描述与多智能体

> 本篇回答：**能力从哪来？**
> 读完你能：用现成工具（含 MCP）、写自己的工具、给工具做 Agent 级定制，
> 并组建一个编排者 + 工人的多智能体系统。

## 3.1 三层能力描述：全框架最重要的结构

flowing 里一切“能力”（Tool、子 Agent、Skill）共享同一模式，三个维度
**各自独立演化、互不侵入**：

| 维度 | Tool | 子 Agent | Skill |
|---|---|---|---|
| 可执行对象 | `Tool`（`execute()`） | Agent 类 | Skill 内容 |
| LLM 可见声明 | `ToolDefinition` | catalog XML 条目 | catalog XML 条目 |
| Agent 级绑定 | `ToolEntry` | `SubagentEntry` | `SkillEntry`（扩展） |

绑定层独立存在的理由：**同一能力在不同 Agent 上应呈现不同的 LLM 视图**。
`FinishTool` 在 ReviewerAgent 上暴露 `score`/`pass`/`issues`，在
PaymentAgent 上暴露 `transaction_id`/`charged_amount`——通过 Agent 级绑定
覆写实现，不改全局注册表、不改工具本身。记住这条主线，本篇所有机制都是
它的展开。

另一条铁律（第 01 篇已见）：**注册 ≠ 可见**。`Runtime` 构造时注册了全部
内置工具，但 LLM 只看得到 Agent 显式声明（`tools:` / `add_tool`）的条目。
可写文件、执行命令等危险工具不会被静默附加。

## 3.2 工具线第一步：声明使用（零代码）

### 内置工具

`builtin::` 命名空间的出厂件（`builtin::read` / `write` / `bash` /
`edit` / `grep` / `glob` / `finish` / `subagent-invoke`，另有标准子
智能体 `builtin::explore-agent`）。声明即可用：

```yaml
tools:
  - read      # 裸名：注册表裸名视图 default:: > builtin:: 命中
  - finish
```

### MCP：接入外部工具服务器

`type: mcp` 把 MCP server 的一组工具变成你的工具（凭证经 `{{ env.X }}`
注入，装配期缺失即报错）：

```yaml
# MCP 工具声明
name: search
type: mcp
description: 搜索互联网内容。
command: npx
args: ["-y", "@modelcontextprotocol/server-brave-search"]
env:
  BRAVE_API_KEY: "{{ env.BRAVE_API_KEY }}"
```

声明块是**组代理**：`list_tools()` 展开后每个服务端工具注册为
`<声明名>--<server 工具名>`（如 `search--brave_web_search`），Agent 侧按
合成名引用。`url`（远程端点）与 `command`（本地 stdio）互斥。

### cli / request：把命令与 HTTP API 声明为工具

```yaml
# type: cli —— Jinja2 命令模板，插入值自动 shlex 转义
name: run-tests
type: cli
description: 运行项目测试套件。
command: cd {{ working_dir }} && python -m pytest {{ test_path }}
args:
  working_dir: {type: string, description: 项目根目录的绝对路径}
  test_path: {type: string, default: src/, description: 测试路径}
```

```yaml
# type: request —— 参数自动映射 body/query
name: create-order
type: request
description: 创建新订单。
url: https://api.example.com/v1/orders
method: POST
headers:
  Authorization: "Bearer {{ env.SHOP_API_KEY }}"
args:
  user_id: {type: string, description: 用户 ID}
output: {type: object, properties: {order_id: {type: string}}}
```

要点各一句：cli 的非零退出码是**正常输出**不是 error；原始拼接须显式
`{{ x | raw }}` 且框架告警。request 的 URL 是两阶段模板（`{{ env.X }}`
装配期渲染、路径参数执行期渲染），`auth` 语法糖优先于 `headers`。
这里的关键边界是：cli 将进程退出状态与标准输出作为工具结果；request
将声明参数映射为 HTTP 请求；MCP 声明则把一个 server 的多个工具汇聚到
同一命名空间中。三者都必须显式绑定到 Agent 才会进入模型上下文。

## 3.3 工具线第二步：写 ScriptTool

需要自己的逻辑时写 `ScriptTool` 子类——“零散参数进、普通值出”，不需要
知道 `ToolResult` 的存在：

```python
from flowing import ScriptTool
from pydantic import BaseModel, Field

class PayArgs(BaseModel):
    order_id: str = Field(description="订单 ID")
    amount: float = Field(ge=0.01, description="支付金额")

class MakePayment(ScriptTool):
    """对指定订单发起支付。仅在用户明确确认支付意图后调用。"""

    name = "make-payment"          # 必填：不由类名推断
    args_model = PayArgs           # 声明即模型：LLM schema 与执行校验同源

    async def execute(self, *, order_id: str, amount: float,
                      caller: Agent) -> dict:   # caller 可选，框架自动注入
        return await payment_service.charge(order_id=order_id, amount=amount)
```

要点：

- `name` 必填（文件通道由文件名/目录名注入并做一致性断言）；
- `args_model` 可省略——从 `execute()` 签名的类型标注推导；`description`
  按 显式声明 > 类 docstring 整体 > execute docstring 整体 回退；
- 返回值自动包装：普通值 → `completed`；抛普通异常 → **`error`（LLM 可见
  的正常产物，不触发错误钩子）**；`raise Intercepted` → `blocked`；
- 三条等价定义通道：手写子类 / `@flowing_tool` 打标函数 / `.fya` 的
  `callable:` 指针（打标与指针互斥）；
- 后台形态（长任务）：`execute` 写成 async generator（首 yield 即收据，
  后续 yield 逐段以 EVENT 消息投递）、或普通 async + `background = True`、
  或返回 `asyncio.Task`——框架统一给 `pending` 收据，不阻塞回合。

## 3.4 工具线第三步：ToolEntry 做 Agent 级定制

`add_tool` / `tools:` 声明产出的是 `ToolEntry`——“这个 Agent 如何使用
这个工具”的绑定。覆写四件套：

```yaml
tools:
  - make-payment as pay:            # as：LLM 看到的别名
      description: "发起支付"
      args:
        amount: {description: "支付金额（元），上限 50000"}  # 稀疏补丁 → override_params
        currency: USD                     # 裸值 → specified（LLM 不可见的固定值）
        user_id: "{{ self.inject('user_id') }}"   # 注入表达式 → specified
        working_dir as cwd: _             # 参数改名 → param_aliases（_ = 空补丁）
```

**参数优先级**：specified（含注入表达式）> LLM 传入 > schema 默认值。
specified 对 LLM 不可见、不可被覆盖——`user_id` 这类宿主上下文值走这个
防篡改通道；注入表达式在调用时以调用方 Agent 为上下文求值，沿 provide 链
上溯（找不到抛 `MissingProvideError`）。

`visible=False` 的条目不进 `Context.tools`（LLM 不可见）但仍可编程式
调用——可见性与可执行性分离。

## 3.5 子 Agent 线：声明、唤起与生命周期

子 Agent 与工具同构，但 LLM 可见面不是独立工具，而是
**`<available_subagents>` catalog**（每次组装现场渲染进 system_prompt）
+ 一个统一的 `subagent-invoke` 工具：

```yaml
# 编排者 root.fya
tools:
  - subagent-invoke
  - finish
subagents:
  - ./translator.fya           # 单文件形态：直接指向 Agent 定义
  - coder as coder:            # 裸名/限定名 + as 别名 + 覆写
      description: 代码审查员，只读
      args:
        strictness: "high"     # specified：LLM 不可见
```

`subagents:` 声明的是**类型绑定，不是实例**。实例在唤起时诞生：

- LLM 路径：`subagent-invoke(name="my-coder", agent_type="coder",
  prompt="...")` → 新建并登记语义名；之后 `resume="my-coder"` **续接同一
  实例**（有记忆）；
- 程序化路径（钩子/工具/外部代码内）：
  `child = await self.create_subagent("coder", task_id="t1")` →
  `await child.query(...)` → `await child.destroy()`；
- 结果是 `SubagentResult`：`result`（最终产出，finish 结构化 dict 或文本）
  与 `subagent_status`（回合结局）**分离**——子 Agent 被取消时已产出的
  内容照返，取消事实不污染内容。

**生命周期三档遗忘**：`destroy()` 丢实例、池 key 保留（`get_agent` 触发
“有 key 无 value → 现场恢复”，记忆延续）→ `archive_agent()` 整棵子树
出池、文件留档 → 物理删除（框架不提供，应用层自做）。Agent 默认存续，
靠池管理，没有 keep_alive 语义。

## 3.6 多智能体拓扑：一棵以 Runtime 为根的树

对象图是一棵树：Runtime（`runtime-0`）是根，Agent 经 `_parent_id` 挂到
亲节点；provide/inject 沿亲代链上溯（终点 Runtime），destroy 沿子树递归。
这套结构带来两个直接推论：

- **跨层共享用 inject**：根 Agent `provide("workspace_root", ...)`，任意
  深度的子 Agent `inject` 可得（凭证放深层节点 provide，收窄可见范围）；
- **崩溃恢复沿树进行**：`recover_agent` 向上递归恢复亲代链，子代靠
  `get_agent` 惰性现场恢复。

协作通道三条：LLM 路由（catalog + subagent-invoke，编排者模式）；程序化
fan-out（`create_subagent` + `asyncio.gather`，注意跨 Agent 等待不得成环）；
消息层（PEER/SUBAGENT 消息入队，`steer()` 运行中导向）。

## 3.7 完整示例：编排者与翻译专家

本例展示编排者将翻译工作委派给子 Agent，再以结构化结果交付。需要
Python 3.13 或更高版本、已安装的 Flowing，以及由环境变量提供的 DeepSeek
API 凭证。以下是完整文件内容；配置中只保留凭证占位符。

`main.py`：

```python
"""入口：launch 导入本文件并等待 main() 返回 Runtime。"""

from flowing import Runtime


async def main() -> Runtime:
    runtime = Runtime(persist_dir="@/.flowing")
    # runtime.set_providers("@/providers.yaml")
    # runtime.set_models("@/models.yaml")
    runtime.set_model_tags("@/model-tags.yaml")
    await runtime.mount("@/root.fya", agent_id="agent-main")
    return runtime
```

`root.fya`：

```yaml
description: 任务编排者：把翻译任务派给翻译专家，汇总交付。
model_tag: default
tools:
  - subagent-invoke
  - finish
subagents:
  - ./translator.fya
---
$system_prompt:
你是编排者。收到翻译请求时，必须调用 subagent-invoke 把它派给翻译专家
translator，拿到译文后用 finish 交付，不要自己翻译。
```

`translator.fya`：

```yaml
description: 翻译专家：把任意文本忠实翻译为用户指定的语言。
model_tag: default
tools:
  - finish
---
$system_prompt:
你是翻译专家。把收到的文本忠实、自然地翻译为指定语言，只输出译文本身，
然后用 finish 交卷。
```

`providers.yaml`：

```yaml
deepseek:
  adapter: deepseek
  base_url: https://api.deepseek.com
  api_key: "{{env.DEEPSEEK_API_KEY}}"
```

`models.yaml`：

```yaml
deepseek-flash:
  provider: deepseek
  model: deepseek-v4-flash
```

`model-tags.yaml`：

```yaml
tags:
  default: deepseek-flash
```

在包含这些内联文件的当前工作目录设置凭证并启动交互界面：

```console
$ export DEEPSEEK_API_KEY='<your DeepSeek API key>'
$ flowing repl .
```

输入：

```text
请把 'hello world' 翻译成中文。
/exit
```

一次记录到的交互结果如下。模型措辞可能变化；子 Agent 的调用参数、
结构化交付内容和消息顺序体现了本例要说明的机制：

```text
(agent-main)>>> 请把 'hello world' 翻译成中文。
[thinking] (reasoning trace omitted)
[tool_call] subagent-invoke {"agent_type": "translator", "prompt": "请把以下文本翻译成中文（简体）：hello world"}
[tool:completed] subagent-invoke ->
[tool_call] finish {"summary": "译文：你好，世界"}
[tool:completed] finish ->
(agent-main)>>> /exit
```

`subagent-invoke` 根据 catalog 选择类型并创建子 Agent；任务提示作为调用参数
传入。子 Agent 以 `finish` 返回译文，编排者再以 `finish` 交付结构化结果，
因此 REPL 正文没有额外的自然语言回复。

## 3.8 小结

1. 三层能力描述：可执行对象 / LLM 可见声明 / Agent 级绑定，独立演化；
2. 工具线：声明使用（builtin/MCP/cli/request）→ ScriptTool 写作 →
   ToolEntry 覆写；参数优先级 specified > LLM > 默认值；
3. 子 Agent：类型绑定 + catalog + `subagent-invoke`；`name=`/`resume=`
   续接；遗忘三档；
4. 拓扑即树：inject 跨层共享，恢复沿树进行。
