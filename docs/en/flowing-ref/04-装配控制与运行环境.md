# 04 · Assembly and Control: Hooks, Injection, and the Runtime Environment

> This chapter answers: **How do I assemble and control?**
> After reading you will be able to: assemble agents at the right time, use hooks
> for interception and observation, manage data with injection and state bags,
> understand cancellation semantics, and embed the system into a real runtime
> environment.
> This chapter applies the principle that **mechanisms live in the core and
> policies live in extensions** to assembly and runtime control.

## 4.1 Assembly timing: setup() and two pairs of lifecycle hooks

Chapter 01 gave the skeleton of the creation pipeline; this section pins down
the timing rules:

- `setup()` does only **state assignment, hook registration, inject reads, and
  Composable calls**; network access and heavy I/O belong in tools. Both the
  create and recover pipelines execute the same `setup()` on a fresh instance —
  exactly once per instance, with consistent assembly results;
- The two hook pairs are fully independent: `before_create`/`after_create` fire
  only in the creation pipeline, and `before_recover`/`after_recover` fire only
  in the recovery pipeline. Logic that "should only run at creation" goes in
  the former (note it can only be declared via `@on('before_create')` on the
  class — `setup()` has not run at that point);
- After `setup()` the framework performs a PENDING check: creation fails if a
  required field (such as `system_prompt`) is not fulfilled, and `@on`
  pointing at an undeclared hook point also fails — fail fast, with no
  half-assembled instance left behind;
- `**kwargs` is persisted into `meta.json` and passed through on recovery —
  **it must be JSON-serializable**, because it is part of the agent's identity;
  host-machine objects (connection pools, etc.) go through `provide` /
  Resource.

## 4.2 The hook system: instance-level, rewritable, blockable

Every agent holds an independent hook registry (`agent.hooks`); all hooks take
effect only for the current instance. Handlers share the signature
`(agent, value)` and have three exits: return the (rewritable) value /
`raise Intercepted` for a hard block / let a normal exception propagate. Two
ways to register:

```python
from flowing import on

class OrderAgent(Agent):
    @on("before_tool_call")              # declared on the class (registered at __init__)
    async def _guard(self, tool_call):
        # command content check: block if it contains rm -rf
        if tool_call.name == "bash" and "rm -rf" in tool_call.args["command"]:
            raise Intercepted("command contains rm -rf; blocked")   # → ToolResult.blocked
        return tool_call

    async def setup(self):
        self.hooks.after_turn(self._audit)   # registered inside setup (instance level)

    async def _audit(self, agent, turn):
        log.info("turn done: aborted=%s msgs=%d", turn.aborted, len(turn.message_ids))
        return turn
```

All three exits appear in `_guard`: returning the (rewritable) `tool_call` is
a pass (editing parameters along the way is a rewrite — for example, rewriting
a dangerous command into a safe form); `raise Intercepted` is a rejection —
the LLM receives the `blocked` result with the reason and can explain to the
user that "the operation was intercepted" rather than "execution failed", and
the typical response is to retry with a safer formulation; a normal exception
propagates directly, and no catch-all hook intercepts it. The decision power
always stays in your handler; the framework only provides the interception
mechanism.

**From interception to approval**: `before_tool_call` is inherently a
human-approval gate — the handler is `async`, so it can `await` an external
confirmation before choosing one of the three exits (`await`ing a normal
coroutine inside a handler is safe; the deadlock ban applies only to
`await query()`). The approval channel is first of all **just one of your own
methods**: hooks are the mechanism, and `confirm` is your policy — it can
freely call external functions (popup, IM inquiry, HTTP callback ... depending
on your application form):

```python
class OrderAgent(Agent):
    @on("before_tool_call")
    async def _approval(self, tool_call):
        if tool_call.name == "bash" and "rm -rf" in tool_call.args["command"]:
            if not await self.confirm(tool_call.args["command"]):
                raise Intercepted("the user rejected this command")
        return tool_call

    async def confirm(self, action: str) -> bool:
        # approval channel: your application form — popup, IM bot, WebSocket inquiry ...
        return await ask_user(action)
```

The point: what the framework provides is the mechanism of "an awaitable,
blockable hook point"; "whom to ask, how to ask, and what to do after asking"
is policy, and the starting point is an ordinary method on the agent.

A quick tour of hook points by family follows:

| Family | Representative hook points | Typical uses |
|---|---|---|
| Lifecycle | `before_create` / `after_create` / `before_recover` / `after_recover` / `before_destroy` / `after_destroy` | Assembly supplements, rebuilding derived structures |
| Turn | `before_turn` (additive injection) / `on_turn_abort` / `after_turn` (the only all-path finalization observation point) | Reminder injection, counting, auditing |
| Message | `on_enqueue` (can reject) / `on_dequeue` (can transform the batch) / `on_turn_append` | Content moderation, streaming to the screen |
| Model | `before_provider_gen` (can rewrite the Context) / `after_provider_gen` / `on_provider_delta` / `on_provider_error` | Context rewriting, streaming UI, error handling (observe / switch model / retry) |
| Tool | `before_tool_call` (interception gate) / `on_tool_yields` (product-level: sync result / receipt / segments / final value, with metadata) / `after_tool_call` | Interception and approval, content scanning, result rewriting, cache short-circuit |
| Subagent | `on_subagent_invoke` / `on_subagent_returns` | Invocation interception, result rewriting |
| Other | `on_fork` / `before_cancel` / `after_cancel` | Fork guards, cancellation guards |

Three common mistakes: `Intercepted` is an **intentional hard block** (it
subclasses `Exception` directly and sits outside the exception hierarchy) —
interception in `before_tool_call` → `blocked` (the tool never ran),
interception in `after_tool_call` → `blocked` (the result was produced but
discarded); an exception in an `after_turn` handler does not wedge the agent
(waiters still receive their results); `watch(name, handler)` is a purely
observational assignment-event channel (fire-and-forget), not a hook point.
The division of labor between the two tool-result hooks: `on_tool_yields` is
product-level — it fires once per synchronous result, background receipt,
segment, and final value, and the value carries `name` / `tool_call_id` /
`production` metadata, making it the landing point for content scanning and
product rewriting; `after_tool_call` is call-level — one invocation per
`tool_call()` call (including the shortcut path), handling result disposition.

## 4.3 provide-inject and state bags: two data channels

**provide/inject** handles "runtime values shared across layers":
`provide(key, value)` registers, and `inject(key)` ascends the `_parent_id`
chain from nearest to farthest (ending at the Runtime), raising
`MissingProvideError` if not found. Rules:

- Writing the same key overwrites, and lookups are real-time — the canonical
  channel for switching configuration (such as locale) at runtime;
- **Sensitive-data boundary**: injected values do not enter the message stream,
  the LLM context, or the disk; but they are visible to descendants along the
  chain — credentials should be provided at a **deep node** to narrow the
  visible scope;
- Provide values that affect assembly before `mount()`; heavy resources shared
  across agents (connection pools, indexes) go through `register_resource` (a
  direct reference outside the tree, not through the injection chain).

**State bags** handle "business state that must be persisted":

```python
async def setup(self):
    self.state.register("visit_count", 0)   # the default is written immediately (write-through)

# read/write (write-through does not trigger watch)
self.state["visit_count"] = self.state["visit_count"] + 1
```

`agent.state` is the default bag (`state.jsonl`), and
`register_state("name")` opens an independent named bag; the Runtime side
additionally has global bags (`core` registered / `default`). On recovery
**persisted values take precedence** — a register default in setup will not
overwrite a persisted value.

## 4.4 Control flow: cooperative cancellation and error decisions

**Cancellation is cooperative**: `cancel()` sets a flag (on all execution
entries and the current turn), and the execution body decides at checkpoints
whether to stop immediately / ignore the flag and complete / wrap up and return
partial results — cancel is normal termination, not an error. The granularity
family: `abort_turn()` (terminates only the current turn) <
`cancel_by_tag()` / `cancel_children()` < `cancel()` (the whole agent);
`stop()` is an imperative entry point reserved for subclass overrides (by
default equivalent to cancel). `pause()` / `resume()` suspend the work-loop
checkpoints (including the `_recursive` subtree variants). `raise Intercepted`
inside `before_cancel` can **prevent cancellation** (for uninterruptible
situations such as an already-submitted payment).

**Provider errors** are always dispatched through the `on_provider_error` hook
(including `ContextLengthError` from token overflow — resending the original
request will reproduce it for sure, but compressing history, switching to a
larger-window model, or merely observing are all legitimate handler
dispositions). This hook is a general-purpose channel: the handler may only
observe (log, alert, report to monitoring), may switch models (`self.model` /
`model_tag`), may `abort_turn()` to terminate the turn actively, or may write
`can_continue=True` after backoff to retry within the turn — **whether to act,
and which action to take, is logic inside the handler**. The framework reads
only one field: `can_continue=False` (the default) ends the turn with `error`
(the agent survives); `True` re-initiates `provider_gen`. The builtin
`use_retry` is just one optional handler hanging on this channel; when it is
not enabled the channel still dispatches as usual — there is simply nobody
rewriting the decision field.

**Policies live outside the core**: retry, compaction, and interception rules
are all outside the core — the builtin Composables `use_retry(agent)` /
`use_compact(agent)` / `use_auto_compact(agent)` /
`use_system_reminder(agent)` / `use_prompt_until(agent)` are the demonstration:
inject policies through `use_xxx(agent, ...)` functions. A common form declares
hook points and registers handlers; a Composable may also attach Agent
attributes, register state, or perform other application-layer logic. Transient
state may live in a closure or an Agent attribute. Keeping state in a closure
created by that call avoids collisions with Agent attribute names, but
external code cannot access it through the Agent; Agent attributes are externally accessible and
manageable, but their names must avoid collisions. State that must persist can
use Flowing's built-in `agent.state.register()` or application-managed
persistence and recovery; closure variables and ordinary Agent attributes do
not provide persistence by themselves. The same Composable can
be called with different parameters. The framework does not deduplicate calls;
the function determines how repeated calls combine. Handlers can be grouped
by `by` when they need to be removed as a group.

## 4.5 Runtime environment: main() policy, the configuration chain, and embedding

**`main()` is the policy layer**: the create/recover branch, idempotent mount
with a fixed `agent_id`, plugin `install` (must happen before the first mount;
installing late has no effect on already-created agents), root-level
provide/Resource registration — all of it lives in these few functions.
Post-recovery operations: the parent chain is recovered upward automatically,
descendants are recovered lazily on the spot, and `archive_orphans()` cleans up
orphans left behind by crashes.

**Configuration chain** (orthogonal to the three model files): framework
defaults < project-level `@/config.yaml` < user-level
`$FLOWING_CONFIG_HOME/config.yaml`, with the runtime `set_config` override
layer taking highest precedence; `FLOWING_*` environment variables are read
directly by their respective consumers (paths and switches).

**Embedding into a host application** (the canonical form beyond the CLI):
the host holds the Runtime returned by `launch` — input goes through
`query`/`message`/`steer`, **output goes through hook subscriptions**
(`on_provider_delta` streaming to the screen, `after_turn` completion
notifications, `before_tool_call` for call interception), and configuration
connects to the host's system via `set_config`/`provide`. Three boundaries:
`@` contexts are isolated per Task, and multiple Runtimes can coexist (use
subprocesses for strong isolation); after `launch` returns, module-level
`resolve()` is unavailable — use `runtime.resolve_path`; **`shutdown()`
responsibility transfers to the host** (write-behind needs draining; exiting
the process without shutdown loses trailing records).

**Observation**: `runtime.snapshot()` / `agent.snapshot()` are read-only
consistent snapshots (a pull channel; pushing relies on hooks); all fields are
JSON-serializable, and sensitive values (provide contents) never enter them.

## 4.6 Summary

1. `setup()` should remain lightweight, and the two lifecycle hook pairs are
   independent; `kwargs` form part of an agent's identity.
2. Hooks are the sole extension bus, and handlers can rewrite values or use
   `Intercepted` to block an operation.
3. Inject shares runtime values, state bags persist application data, and
   Resources hold heavy assets.
4. Cancellation is cooperative, and provider errors have a decision point.
   **Retry, compaction, and interception rules are policies that live in
   Composables and plugins.** Apply this principle when writing extensions.
5. `main()` is the policy layer, and embedding means holding the Runtime,
   subscribing to hooks, and owning shutdown.
