# 02 · Where Context Comes From: the Message Tree and On-the-Spot Assembly

> This chapter answers: **Where does context come from?**
> After reading you can: understand the message model and the message-level
> tree; see that "context is not state but a view assembled on the spot
> before each call; history supports surgery"; and read the context budget.

## 2.1 Message: the unified representation of all information

User input, LLM responses, tool results, external events, and subagent
reports — all are uniformly represented as `Message`. It is the object-layer
model: **a message has no `role` attribute**; `kind` describes "who this
message comes from", and mapping kind → each vendor's API role is the
responsibility of the Provider adapter (Anthropic `assistant`, OpenAI
`assistant`, Gemini `model`, ...).

The seven-value `MessageKind`:

| kind | From whom | Queued? |
|---|---|---|
| `USER` | User | Enters the queue |
| `PROVIDER` | Model response (including multimodal output) | **Never enters the queue** (produced within a turn) |
| `TOOL` | Tool execution result | Not queued (attached to the tree directly within a turn) |
| `SYSTEM` | Context injection by the framework / a Composable | Dual channel (see §2.4) |
| `PEER` | Sent intentionally by another agent | Enters the queue |
| `EVENT` | An external event or extension-delivered content (such as cron, async tool final values, and Skill bodies) | Enters the queue |
| `SUBAGENT` | Subagent return result | Enters the queue |

`content` is a list of ContentBlocks, and different types may be interleaved:
`TextBlock` / `ThinkingBlock` (carrying the Provider signature) /
`ToolCallBlock` / `StructBlock` (structure to the program, `dumps` text to
the LLM) / media blocks (`ImageBlock`, etc., always base64-inline; `data` is
the authoritative representation).

Two iron rules:

- **Pairing anchor**: in a PROVIDER message, `ToolCallBlock.id` and the
  `tool_call_id` of the subsequent TOOL message are paired strictly 1:1;
  `Message.__post_init__` enforces bidirectionally that `kind=TOOL ⟺ the
  pairing field is not None` — orphan results are eliminated at the
  construction point.
- **kind has no behavioral meaning**: there is no shortcut such as "a pure
  system message does not trigger the LLM"; kind only determines the
  presentation mapping of the adapter.

## 2.2 The message-level tree: history is a surgically modifiable forest

Messages are not only queued — they are also **attached to a tree**. Every
agent holds a message-level tree:

- Node = message (`id` + `parent_id` chain); `parent_id=None` is the root
  marker — **multiple roots are allowed** (a forest model), with no virtual
  root;
- `current_head_id` is the cursor: a new message links to it and the cursor
  then moves forward; context assembly walks `parent_id` from the head up to
  the root;
- **`fork(msg_id)` only moves the cursor** and never creates nodes — the same
  history can hold multiple branches at once (exploring A/B directions), with
  old branches kept intact.

Persistence is `tree.jsonl` in the form of a record stream (one record per
line, append-mostly with periodic compaction rewrites). One sentence for each
of the three persistence markers:

- `turn_end`: when this PROVIDER message is persisted, the turn closes with
  it — recovery uses it to locate complete turn boundaries;
- `partial`: when streaming is interrupted, the accumulated content is
  **still persisted** (not discarded);
- `synthetic`: on recovery, if an orphan tool_call is found (the result
  message is missing), a placeholder TOOL message with a deterministic id is
  synthesized to close the pairing — context is always paired; the adapter
  neither needs to nor should patch it on its own.

**History surgery**: modifying history goes through the five ops of
`agent.chain` (`MessageChain`) — `insert` / `branch` / `remove` / `update` /
`reparent` — a minimal complete set. Each op = modify the in-memory
authoritative chain + synchronously append one change record
(tombstone/move/update); physical rewriting is deferred to compaction time.
Two points that are easy to misuse:

- At a fork point, `insert` **merges** multiple child branches under the new
  message; to add a parallel branch only, use `branch` (`branch(None, msg)`
  is the only entry point for opening a new root — this is exactly the
  scenario of context compaction swapping chains);
- `remove` does not cascade to subtrees: direct children are automatically
  re-attached to the deleted message's parent node, and the chain stays
  continuous.

A "half turn" after `turn_end` (torn by a crash) enters context as usual
after recovery — it is already-produced complete history; it is neither
truncated nor resumed.

## 2.3 Context: the Provider's only input

Before every model call, the agent assembles a `Context` on the spot —
**three orthogonal fields, not a flat message list**:

```python
Context(
    system_prompt=[PromptSegment, ...],   # Layered prompt segments (cache markers preserved)
    tools=[ToolDefinition, ...],          # Declarations of currently enabled tools
    messages=[Message, ...],              # The message path from root to head
)
```

The three-field structure makes the adapter's mapping a mechanical per-field
conversion. Key semantics:

- **On-the-spot evaluation, zero caching**: every assembly re-evaluates all
  Parsables, re-collects the message path, and regenerates tool definitions.
  This is a prerequisite of functional correctness (environment variables and
  instance attributes are always up to date), not a performance choice;
- **No implicit attachment**: builtin tools such as `finish` /
  `subagent-invoke` enter `Context.tools` only if the user explicitly
  declares them (`tools:` / `add_tool`) — registration ≠ visibility;
- The assembly product is sent to the Provider only after the
  `before_provider_gen` hook — a handler may rewrite all three fields
  wholesale (but changing `messages` is not recommended: the change is not
  persisted and is lost at the next assembly).

## 2.4 prompt_blocks: layered registration of the system prompt

The system prompt is not a single piece of text but **layered segments
concatenated in registration order** — the framework skeleton, plugins, and
the application each register and manage their own segments, without
awareness of one another:

```python
async def setup(self):
    self.mode = "presentation mode"
    self.prompt_blocks.append(
        "session-info",
        Parsable("This session is hosted by {{ node_id }}; mode: {{ mode }}."),
        cache="dynamic", by="demo", tags=["demo"],
    )
```

Key points:

- `prompt_blocks[0]` is the lazy reference block injected by the framework
  (its content is the `{{ self.system_prompt }}` template, `by="core"`) —
  change the class attribute `system_prompt` in `setup()` and it is
  reflected automatically at the next assembly; **do not delete it** (the
  system prompt would disappear, and the framework provides no fallback);
- `cache` (static/dynamic/session) is merely an **intent marker** for the
  adapter: the framework does not read or cache it locally;
- Management operations: `disable_by_tag` / `enable_by_tag` /
  `remove_by_owner`, etc. — the regular technique for mode switching
  (register two sets of blocks and toggle them by tag);
- Put dynamic content into Parsable template references (such as
  `{{ current_mode }}`) so that each assembly evaluates it on the spot and
  gets the latest value; high-frequency values (the current time) go through
  the message channel (additive injection into `pending_messages` in
  `before_turn`) — only stable prompt content can hit the provider's prefix
  cache.

`SYSTEM` therefore has a **dual channel**: the prompt_blocks channel (enters
system_prompt every turn, triggers no new turn) and the message-queue channel
(enters history and triggers a new turn).

## 2.5 Context budget: measured anchor plus tail estimation

`estimate_context_tokens()` answers "roughly how large would the context be
if sent to the LLM now": walk up from the head to find the nearest PROVIDER
message carrying measured usage as the **anchor**; the part covered by the
anchor uses the measurement (`measured`), and newer content after it is
estimated with a character heuristic (`estimated`). `usage_ratio` is not
clamped — a value >1.0 is a legitimate overflow signal; it is `None` when
the model declares no `context_window`.

The estimate is an observation API on the Python side (for a quick REPL
health check, use `/status` / `/snapshot`). The complete Workshop example
below includes its runtime files, prompt, inputs, and two interaction results.
The estimate is a recorded sample and varies with language, model usage, and
message history:

```python
est = agent.estimate_context_tokens()
# tokens=1596 measured=1348 estimated=248 ratio=None
#   measured=1348: the measured anchor from the nearest PROVIDER message in the recovered history
#   estimated=248: tail messages after the anchor, estimated; the model declares no context_window → ratio=None
```

Threshold decisions and compaction are **policy**; the framework only
provides observation values. Compaction can use the mechanism foundation from
§2.2: a summary opens a new chain as the new root with `branch(None, msg)`,
then `fork()` moves the cursor — the old tree remains intact and can be
switched back to at any time.

## 2.6 Full example: context estimation after two turns

This example shows how a fixed agent_id recovers the same agent and how context estimation reads the recovered message path. It requires Python 3.13 or later, an installed Flowing package, and your own DeepSeek API credential. All runtime files, configuration, prompts, inputs, and key outputs are listed here. {{env.DEEPSEEK_API_KEY}} is an environment-variable placeholder, not a credential value.

main.py:

~~~python
"""Entry point: launch imports this file and awaits main() to return a Runtime."""

from flowing import Runtime


async def main() -> Runtime:
    runtime = Runtime(persist_dir="@/.flowing")
    # runtime.set_providers("@/providers.yaml")
    # runtime.set_models("@/models.yaml")
    runtime.set_model_tags("@/model-tags.yaml")
    await runtime.mount("@/root.fya", agent_id="agent-main")
    return runtime
~~~

from flowing import Parsable

    self.mode = "presentation mode"
    self.prompt_blocks.append(
        "session-info",

        agent.state["visit_count"] = agent.state["visit_count"] + 1

inspect_context.py:

~~~python
import asyncio

from flowing import launch


async def main():
    runtime = await launch(".")
    try:
        agent = await runtime.get_agent("agent-main")
        if agent is None:
            raise RuntimeError("agent-main is not available")
        estimate = agent.estimate_context_tokens()
        print(
            f"tokens={estimate.tokens} measured={estimate.measured} "
            f"estimated={estimate.estimated} ratio={estimate.usage_ratio}"
        )
    finally:
        await runtime.shutdown()


asyncio.run(main())
~~~

Run python inspect_context.py in the same working directory. One recorded result is:

~~~

measured is the anchor supplied by the nearest Provider message in the recovered history that has measured usage. estimated covers new content after that anchor. Exact values vary with language, model replies, and the message path; ratio is None when the model declares no context_window.

## 2.7 Summary

1. Information is uniformly represented as `Message`; kind describes the
   source, and role mapping belongs to the adapter.
2. History is a message-level tree (forest and head cursor); `fork()` switches
   the view, and five operations modify the history.
3. `Context` has three orthogonal fields and is **assembled on the spot**
   before every call; lazy evaluation is a correctness prerequisite.
4. The system prompt is registered in layers; budget observation is
   separated from compaction policy.
