# 01 · Message-Driven Agents: The Runtime Model

> This chapter answers: **How does the system run?**
> After reading you can: configure model access, bring up a flowing
> subproject, complete a conversation, and understand how messages drive
> turns.

## 1.1 What a flowing subproject contains

A flowing application is assembled as a subproject. The minimal Q&A example
uses these project files and user-level configuration:

| Filename | Purpose |
|---|---|
| `main.py` | Entry point; `launch` imports it and awaits `main()` to return a Runtime. |
| `root.fya` | Declarative definition of the root agent. |
| User-level `providers.yaml` | Provider adapter, endpoint, and credential environment-variable placeholder; shared by subprojects by default. |
| `models.yaml` | Binding from a model to a Provider entry. |
| `model-tags.yaml` | Mapping from a tag to a model entry. |

`root.fya` is the declarative agent definition (`.fya` = flowing agent/tool
declaration file):

```yaml
description: Minimal Q&A assistant
model_tag: default
---
$system_prompt:
You are a concise English Q&A assistant. Keep your answers within three sentences.
```

The YAML header declares metadata; the named `$system_prompt:` block after
the `---` separator is the system prompt (the only required field). There is
no Python code at all — this is already an agent with full behavioral
capability.

`main.py` is the subproject entry point, responsible for **assembly**:
constructing the Runtime, registering model sources, and mounting the root
agent:

```python
"""Entry point: launch imports this file and awaits main()."""

from flowing import Runtime

async def main() -> Runtime:
    runtime = Runtime(persist_dir="@/.flowing")
    # runtime.set_providers("@/providers.yaml")
    # runtime.set_models("@/models.yaml")
    runtime.set_model_tags("@/model-tags.yaml")
    # Fixed agent_id → idempotent mount: the second startup goes through
    # recovery — "the same root is back"
    await runtime.mount("@/root.fya", agent_id="agent-main")
    return runtime
```

For the first Provider setup, run `flowing-config providers add` and press Enter
at the path prompt to write to the default user-level `providers.yaml` (normally
`~/.flowing/providers.yaml`, overridable with `FLOWING_CONFIG_HOME` or
`FLOWING_PROVIDERS_PATH`). Runtime loads it automatically. Later subprojects can
reference the same Provider entry name from `models.yaml` without creating another
`providers.yaml` or calling `set_providers()`. Uncomment `set_providers()` and provide
a project-level file only when a subproject needs its own Provider configuration.

Note: the root agent is mounted with `mount()`; with a fixed `agent_id` the
mount is idempotent — the first startup creates the root, and the second
startup finds the same id already in the pool and automatically goes through
the recovery pipeline, so "the same root is back"; `None` creates a new one
on every start.

## 1.2 Model access: three YAML files and the two-hop model_tag resolution

The number one reason an agent system fails to start is a mismatched model.
flowing splits model access into three files, each with a single
responsibility and independently replaceable:

```yaml
# providers.yaml — provider entries: one entry = one API key identity
deepseek:
  adapter: deepseek
  base_url: https://api.deepseek.com
  api_key: "{{env.DEEPSEEK_API_KEY}}"   # Credentials are injected from environment variables, not hard-coded
openrouter:
  adapter: openrouter
  base_url: https://openrouter.ai/api/v1
  api_key: "{{env.OPENROUTER_API_KEY}}"
```

```yaml
# models.yaml — model entries: each entry is one concrete model and selects a provider entry
deepseek-flash:
  provider: deepseek
  model: deepseek-v4-flash
openrouter-gpt-6-luna:
  provider: openrouter
  model: openai/gpt-6-luna
  "reasoning.effort": high
```

```yaml
# model-tags.yaml — tag → model entry name mapping (single value, no fallback chain)
tags:
  default: deepseek-flash
  luna: openrouter-gpt-6-luna
```

How does `model_tag: default` in an agent declaration become a real API call?
**Two-hop resolution**:

```
model_tag("default") ──① model-tags.yaml──▶ entry name ("deepseek-flash")
                     ──② models.yaml──────▶ ModelConfig(provider=deepseek,
                                             model=deepseek-v4-flash)
model_tag("luna")    ──① model-tags.yaml──▶ entry name ("openrouter-gpt-6-luna")
                     ──② models.yaml──────▶ ModelConfig(provider=openrouter,
                                             model=openai/gpt-6-luna,
                                             extra={"reasoning.effort": "high"})
```

The three files declare provider identities, models, and tag mappings separately.
The `provider` field in `models.yaml` selects an entry from `providers.yaml`, while
`model` is the model ID sent to that provider. A tag points only to a model entry.
The `default` tag still selects DeepSeek. Set an agent's `model_tag` to `luna` to
call `openai/gpt-6-luna` through OpenRouter; this requires `OPENROUTER_API_KEY`.
The literal extension key `"reasoning.effort": high` belongs to that model entry
and is sent to OpenRouter with GPT-6 Luna. The DeepSeek entry has no such setting.

Rules: an undefined tag falls back to the `default` tag; if `default` is also
undefined → an error is raised, with **no silent fallback**. `{{env.X}}` is
substituted at entry load time; a missing environment variable is substituted
as an empty string with a `warnings.warn` warning, and **loading is not
interrupted** (when you configure multiple entries but use only one, the other
entries do not need their environment variables to be present; the practical
consequence of missing credentials — such as a 401 — surfaces at that entry's
first call via `on_provider_error`). The source path defaults to
`$FLOWING_CONFIG_HOME/` (it can be overridden by an environment variable or
programmatically via `set_providers`, etc.; see Chapter 04 §4.6).

## 1.3 launch and Runtime: the object-graph root

`flowing.launch(path, **kwargs)` is the **only entry point** for creating a
Runtime. It does very little: register the `@` project-root context (the
resolution base for the `@/` path prefix, isolated per asyncio Task) → import
the subproject `main.py` → `await main(**kwargs)` → reset the context. It
does not parse configuration, does not know about plugins, and does not open
ports — all of that lives in `main()` or further out.

The framework's built-in **REPL** (the `repl` subcommand) is a minimal
interactive observation window built on `launch` — just the tool for running
the first example to see the effect: non-`/` input is delivered to the bound
agent via `query()`, and `/xxx` is a control command (it does not enter the
message stream):

```console
$ flowing repl .
(agent-main)>>> Introduce yourself in one sentence.
I'm a concise English Q&A assistant designed to answer your questions clearly and briefly.
[thinking] (reasoning trace omitted)
I'm a concise English Q&A assistant designed to answer your questions clearly and briefly.
(agent-main)>>> /exit
```

(The programmatic `await flowing.launch(...)` is the entry point when
embedding into a host application; see Chapter 04 §4.5.)

The Runtime is the **object-graph root**: it holds all agent nodes
(`_nodes`), the global tool registry (`tool_registry`) and the agent-type
registry (`agent_registry`), the agent pool, and the provide store (the end of
the injection chain). Its `node_id` is fixed as `"runtime-0"`; the root
agent's `_parent_id` points to it — the topology of a multi-agent system is a
tree rooted at the Runtime (see Chapter 03).

Two frequently used semantics:

- **`await runtime`** blocks until `shutdown()` — the CLI / the embedding
  party uses it to keep the process alive;
- **`shutdown()`** recursively destroys all agents (draining their persistence
  backends) → runs plugin finalization → closes the global state view.
  Persistence is write-behind (commits are only queued); exiting the process
  directly without `shutdown()` loses the tail records. The REPL's `/exit`
  (or Ctrl-D) takes exactly this path.

## 1.4 Agent: queue, worker loop, and logical turns

Every agent instance owns: a **priority message queue**, a **resident
worker-loop Task**, a **message-level tree** (Chapter 02), and a set of
instance-level hooks (Chapter 04). Creating an agent starts its worker loop;
from then on, all behavior is message-driven.

User input, model responses, tool results, external events, and subagent
reports are all uniformly represented as `Message` in the framework. **A turn
can only be triggered by a message**: a cron firing, an async tool
completing, or a subagent delivering results — each first becomes a message
that is enqueued and then consumed by the worker loop; even steering and
interruption are priority-carrying messages (STEER / INTERRUPT), not
out-of-band signals.

**Messages in** — three entry points, chosen by whether you need a result:

```python
result = await agent.query("Look up order 4521 for me")      # Await the turn product (TurnResult)
mid = await agent.message("Remind me to drink water later")  # Fire-and-forget; only the message id
await agent.steer("Change the budget cap to 500")            # Steer a turn in progress (STEER priority)
```

**Turns out** — the worker loop consumes the queue serially; each (batch of)
message drives one **logical turn**: assemble context → call the model →
possibly execute tools → finish when the response has `finish=True`. What
`query()` awaits is a `TurnResult`:

```python
result.status       # "completed" / "blocked" / "cancelled" / "error"
result.final_text   # Text of the last PROVIDER message of this turn
result.token_usage  # Aggregated token usage of this turn
```

All four outcomes **will** resolve to the waiter — a crash, cancellation, or
`destroy()` will never leave the caller of `query()` hanging.

**The deadlock prohibition** (the most common pitfall for newcomers): calling
`await query()` anywhere inside the current turn's call stack (inside any
hook or tool `execute`) deadlocks for sure — the turn's completion must wait
for the hook to return, the hook waits for the next turn, and the next turn
waits for the current turn to complete. The same applies to cross-agent wait
cycles (A waits for B, B waits for A). When you need to drive the agent from
inside a turn, use `steer()` (visible in the current turn's context,
non-interrupting), not `query()`.

## 1.5 The creation pipeline and setup()

Agent instances are never constructed directly; the only creation path is
`Runtime.create_agent` (both `mount` and `create_subagent` delegate to it).
Key pipeline steps: `__new__` pre-binds identity → `__init__` builds the
synchronous skeleton → writes `meta.json` → `before_create` hook →
**`setup(**kwargs)`** → PENDING check → model resolution → registration →
starting the worker loop.

`setup()` is where you write assembly code (class attributes handle
declaration; setup handles assembly):

```python
async def setup(self, user_id: int, locale: str = "zh"):
    self.user_id = user_id            # State assignment (runtime configuration, not persisted)
    self.locale = locale
    self.add_tool("make-payment")     # Capability binding
    self.provide("user_id", user_id)  # Sensitive values go through the injection channel (Chapter 04)
```

Constraints: `setup()` must be **lightweight** (put network / heavy IO into
tools); `**kwargs` is persisted into `meta.json` and passed through on
recovery, so it must be JSON-serializable — it is part of the agent's
identity.

The recovery pipeline (`recover_agent`) is isomorphic, with one extra step —
replaying the session log — and it fires the `before_recover` /
`after_recover` hook pair, which is **completely independent** of the create
hook pair. After recovery: message history, state bag, and child_ids are all
present; turns in progress are not resumed.

## 1.6 Full example: a Q&A agent

Sections 1.1–1.2 contain the complete contents of `main.py`, `root.fya`, and
the three model configuration files required by this example. The runtime
requires Python 3.13 or later, an installed Flowing package, and your own
DeepSeek API credential, provided only through an environment variable:

```console
$ export DEEPSEEK_API_KEY='<your DeepSeek API key>'
$ flowing repl .
```

Run the command in the current working directory containing the five inline
files, then enter the sample question:

```console
(agent-main)>>> Introduce yourself in one sentence.
I'm a concise English Q&A assistant designed to answer your questions clearly and briefly.
[thinking] (reasoning trace omitted)
I'm a concise English Q&A assistant designed to answer your questions clearly and briefly.
(agent-main)>>> /exit
```

The REPL delivers non-`/` input through `query()`. The model generates the
reply, so its wording may vary. `/exit` triggers `shutdown()` and exits. On
the next startup, the fixed `agent_id` binds the REPL to the same root agent
and enters the recovery pipeline.

The complete journey of one USER message: `query()` packs it and enqueues →
the worker loop dequeues it and opens a turn → context is assembled
(system_prompt + message path + tool declarations) → the Provider responds →
the response message is attached to the tree and persisted → the
`TurnResult` is assembled in finalization → resolved to the waiter.

## 1.7 Summary

Key points of this chapter:

1. A subproject combines `main.py` (assembly policy), a `.fya` agent
   declaration, and the three model configuration files.
2. `launch` is the only entry point, the Runtime is the object-graph root,
   and `main()` decides whether to create or recover an agent.
3. An agent has a queue and a worker loop; `query()` awaits a `TurnResult`,
   and all four outcomes resolve without leaving the caller hanging.
4. Calling `query()` inside the turn stack deadlocks, so use `steer()` instead.
