# 03 · Where Capabilities Come From: Three-Layer Capability Description and Multi-Agent

> This chapter answers: **Where do capabilities come from?**
> After reading you will be able to: use ready-made tools (including MCP), write
> your own tools, customize tools at the agent level, and build an orchestrator +
> worker multi-agent system.

## 3.1 Three-layer capability description: the most important structure in the framework

In flowing, every "capability" (Tool, subagent, Skill) shares the same pattern,
with three dimensions that **evolve independently and never intrude on one
another**:

| Dimension | Tool | Subagent | Skill |
|---|---|---|---|
| Executable object | `Tool` (`execute()`) | Agent class | Skill content |
| LLM-visible declaration | `ToolDefinition` | catalog XML entry | catalog XML entry |
| Agent-level binding | `ToolEntry` | `SubagentEntry` | `SkillEntry` (extension) |

The reason the binding layer exists independently: **the same capability should
present a different LLM view on different agents**. `FinishTool` exposes
`score`/`pass`/`issues` on ReviewerAgent, but `transaction_id`/`charged_amount`
on PaymentAgent — achieved through agent-level binding overrides, without
touching the global registry or the tool itself. Keep this main thread in mind;
every mechanism in this chapter unfolds from it.

The other iron rule (seen in Chapter 01): **registration ≠ visibility**. The
`Runtime` constructor registers all builtin tools, but the LLM only sees entries
the agent explicitly declares (`tools:` / `add_tool`). Dangerous tools such as
writing files or executing commands are never silently attached.

## 3.2 Tool track, step one: declare and use (zero code)

### Builtin tools

Factory pieces in the `builtin::` namespace (`builtin::read` / `write` / `bash` /
`edit` / `grep` / `glob` / `finish` / `subagent-invoke`, plus the standard
subagent `builtin::explore-agent`). Declaring them is enough:

```yaml
tools:
  - read      # bare name: hits the registry's bare-name view, default:: > builtin::
  - finish
```

### MCP: connecting external tool servers

`type: mcp` turns a group of tools from an MCP server into your tools
(credentials are injected via `{{ env.X }}`; a missing value at assembly time
is an error):

```yaml
# MCP tool declaration
name: search
type: mcp
description: Search the internet for content.
command: npx
args: ["-y", "@modelcontextprotocol/server-brave-search"]
env:
  BRAVE_API_KEY: "{{ env.BRAVE_API_KEY }}"
```

The declaration block is a **group proxy**: after `list_tools()` expands it,
each server-side tool is registered as `<declaration-name>--<server-tool-name>`
(e.g. `search--brave_web_search`), and the agent side refers to them by the
composed name. `url` (remote endpoint) and `command` (local stdio) are mutually
exclusive.

### cli / request: declaring commands and HTTP APIs as tools

```yaml
# type: cli — Jinja2 command template; inserted values are automatically shlex-escaped
name: run-tests
type: cli
description: Run the project's test suite.
command: cd {{ working_dir }} && python -m pytest {{ test_path }}
args:
  working_dir: {type: string, description: Absolute path of the project root}
  test_path: {type: string, default: src/, description: Test path}
```

```yaml
# type: request — parameters are automatically mapped to body/query
name: create-order
type: request
description: Create a new order.
url: https://api.example.com/v1/orders
method: POST
headers:
  Authorization: "Bearer {{ env.SHOP_API_KEY }}"
args:
  user_id: {type: string, description: User ID}
output: {type: object, properties: {order_id: {type: string}}}
```

One sentence for each: for cli, a non-zero exit code is **normal output**, not
an error; raw concatenation requires an explicit `{{ x | raw }}` and makes the
framework warn. For request, the URL is a two-stage template (`{{ env.X }}`
rendered at assembly time, path parameters rendered at execution time), and the
`auth` sugar takes precedence over `headers`. The key boundaries are that cli
exposes the process exit status and standard output as a tool result, request
maps declared parameters to an HTTP request, and an MCP declaration groups
one server's tools under a shared namespace. Each must be explicitly bound to
an agent before it enters the model context.

## 3.3 Tool track, step two: writing a ScriptTool

When you need your own logic, write a `ScriptTool` subclass — "loose parameters
in, plain values out", with no need to know that `ToolResult` exists:

```python
from flowing import ScriptTool
from pydantic import BaseModel, Field

class PayArgs(BaseModel):
    order_id: str = Field(description="Order ID")
    amount: float = Field(ge=0.01, description="Payment amount")

class MakePayment(ScriptTool):
    """Initiate payment for the given order. Call only after the user has explicitly confirmed the payment intent."""

    name = "make-payment"          # required: not inferred from the class name
    args_model = PayArgs           # declaration is the model: LLM schema and execution validation share one source

    async def execute(self, *, order_id: str, amount: float,
                      caller: Agent) -> dict:   # caller is optional; injected automatically by the framework
        return await payment_service.charge(order_id=order_id, amount=amount)
```

Key points:

- `name` is required (the file channel injects it from the file/directory name
  and asserts consistency);
- `args_model` is optional — it is inferred from the type annotations of the
  `execute()` signature; `description` falls back in the order: explicit
  declaration > entire class docstring > entire execute docstring;
- Return values are wrapped automatically: a plain value → `completed`; raising
  a normal exception → **`error` (a normal, LLM-visible product that does not
  trigger error hooks)**; `raise Intercepted` → `blocked`;
- Three equivalent definition channels: handwritten subclass / a function marked
  with `@flowing_tool` / a `.fya` `callable:` pointer (marking and pointer are
  mutually exclusive);
- Background form (long tasks): write `execute` as an async generator (the
  first yield is the receipt; later yields are delivered one segment at a time
  as EVENT messages), or plain async + `background = True`, or return an
  `asyncio.Task` — the framework issues a uniform `pending` receipt in all
  cases and does not block the turn.

## 3.4 Tool track, step three: agent-level customization with ToolEntry

Declarations via `add_tool` / `tools:` produce a `ToolEntry` — a binding of
"how this agent uses this tool". Four override pieces:

```yaml
tools:
  - make-payment as pay:            # as: the alias the LLM sees
      description: "Initiate payment."
      args:
        amount: {description: "Payment amount (CNY), upper limit 50000"}  # sparse patch → override_params
        currency: USD                     # bare value → specified (a fixed value invisible to the LLM)
        user_id: "{{ self.inject('user_id') }}"   # injection expression → specified
        working_dir as cwd: _             # parameter rename → param_aliases (_ = empty patch)
```

**Parameter precedence**: specified (including injection expressions) > passed
by the LLM > schema default.

specified values are invisible to the LLM and cannot be overridden —
host-context values like `user_id` travel through this tamper-proof channel;
injection expressions are evaluated at call time in the context of the calling
agent, ascending the provide chain (`MissingProvideError` if not found).

Entries with `visible=False` do not enter `Context.tools` (invisible to the
LLM) but can still be invoked programmatically — visibility is separated from
executability.

## 3.5 Subagent track: declaration, invocation, and lifecycle

Subagents are isomorphic to tools, but the LLM-visible surface is not a
standalone tool; it is the **`<available_subagents>` catalog** (rendered into
the system_prompt on the spot at every assembly) plus one unified
`subagent-invoke` tool:

```yaml
# orchestrator root.fya
tools:
  - subagent-invoke
  - finish
subagents:
  - ./translator.fya           # single-file form: directly names the agent definition
  - coder as coder:            # bare/qualified name + as alias + overrides
      description: Code reviewer, read-only
      args:
        strictness: "high"     # specified: invisible to the LLM
```

`subagents:` declares a **type binding, not an instance**. Instances are born
at invocation:

- LLM path: `subagent-invoke(name="my-coder", agent_type="coder",
  prompt="...")` → creates and registers a new semantic name; afterwards,
  `resume="my-coder"` **resumes the same instance** (with memory);
- Programmatic path (inside hooks/tools/external code):
  `child = await self.create_subagent("coder", task_id="t1")` →
  `await child.query(...)` → `await child.destroy()`;
- The result is a `SubagentResult`: `result` (the final output — a structured
  finish dict or text) and `subagent_status` (the turn's outcome) are
  **separated** — when a subagent is cancelled, already-produced content is
  still returned; the cancellation fact does not contaminate the content.

**Three tiers of lifecycle forgetting**: `destroy()` drops the instance but
keeps the pool key (`get_agent` triggers "key without value → on-the-spot
recovery", and memory continues) → `archive_agent()` removes the entire
subtree from the pool with files archived → physical deletion (not provided by
the framework; the application layer does it itself). Agents persist by default
and are managed by the pool; there is no keep_alive semantics.

## 3.6 Multi-agent topology: a tree rooted at the Runtime

The object graph is a tree: the Runtime (`runtime-0`) is the root, and agents
attach to their parent via `_parent_id`; provide/inject ascends the parent
chain (ending at the Runtime), and destroy recurses down the subtree. This
structure yields two direct corollaries:

- **Use inject for cross-layer sharing**: the root agent provides
  `provide("workspace_root", ...)`, and a subagent at any depth can `inject`
  it (provide credentials at a deep node to narrow the visible scope);
- **Crash recovery proceeds along the tree**: `recover_agent` recursively
  restores the parent chain upward, and descendants are recovered lazily on the
  spot via `get_agent`.

There are three collaboration channels: LLM routing (catalog + subagent-invoke,
the orchestrator pattern); programmatic fan-out (`create_subagent` +
`asyncio.gather` — note that cross-agent waits must not form a cycle); and the
message layer (PEER/SUBAGENT messages are enqueued, and `steer()` redirects a
running agent).

## 3.7 Full example: an orchestrator and a translator

This example shows an orchestrator delegating translation to a subagent and
delivering the result as structured data. It requires Python 3.13 or later,
an installed Flowing package, and a DeepSeek API credential supplied through
an environment variable. The complete file contents follow; the configuration
contains only a credential placeholder.

`main.py`:

```python
"""Entry point: launch imports this file and awaits main() to return a Runtime."""

from flowing import Runtime


async def main() -> Runtime:
    runtime = Runtime(persist_dir="@/.flowing")
    # runtime.set_providers("@/providers.yaml")
    # runtime.set_models("@/models.yaml")
    runtime.set_model_tags("@/model-tags.yaml")
    await runtime.mount("@/root.fya", agent_id="agent-main")
    return runtime
```

`root.fya`:

```yaml
description: "Task orchestrator: dispatches translation tasks to the translator specialist and delivers the collected result."
model_tag: default
tools:
  - subagent-invoke
  - finish
subagents:
  - ./translator.fya
---
$system_prompt:
You are the orchestrator. When a translation request arrives, you must call
subagent-invoke to dispatch it to the translator specialist translator, and
deliver the translation with finish once you receive it. Do not translate it
yourself.
```

`translator.fya`:

```yaml
description: "Translator specialist: faithfully translates any text into the language the user specifies."
model_tag: default
tools:
  - finish
---
$system_prompt:
You are the translator specialist. Translate the text you receive faithfully
and naturally into the specified language; output only the translation itself,
then deliver with finish.
```

`providers.yaml`:

```yaml
deepseek:
  adapter: deepseek
  base_url: https://api.deepseek.com
  api_key: "{{env.DEEPSEEK_API_KEY}}"
```

`models.yaml`:

```yaml
deepseek-flash:
  provider: deepseek
  model: deepseek-v4-flash
```

`model-tags.yaml`:

```yaml
tags:
  default: deepseek-flash
```

Set the credential and start the REPL from the current working directory
containing these inline files:

```console
$ export DEEPSEEK_API_KEY='<your DeepSeek API key>'
$ flowing repl .
```

Input:

```text
Please translate 'hello world' into Chinese.
/exit
```

One recorded interaction is shown below. Model wording may vary; the subagent
call parameters, structured delivery, and message order demonstrate the
mechanics discussed here:

```text
(agent-main)>>> Please translate 'hello world' into Chinese.
I'll dispatch this translation request to the translator specialist.
[tool_call] subagent-invoke {"agent_type": "translator", "prompt": "Translate the following text into Chinese: \"hello world\""}
[tool:completed] subagent-invoke ->
[thinking] (reasoning trace omitted)
[tool_call] finish {"summary": "The translation of \"hello world\" into Chinese is: 你好，世界"}
[tool:completed] finish ->
(agent-main)>>> /exit
```

`subagent-invoke` selects the type from the catalog and creates a subagent;
the task prompt is passed as an argument. The subagent returns the translation
with `finish`, and the orchestrator delivers a structured result with `finish`,
so the REPL has no additional natural-language response body.

## 3.8 Summary

1. The three-layer capability description separates the executable object,
   the LLM-visible declaration, and the agent-level binding so they can evolve
   independently.
2. Tool use progresses from declarations and builtin/MCP/CLI/request tools to
   ScriptTools and ToolEntry overrides; parameter precedence is specified
   value, then LLM value, then default.
3. Subagents combine type binding, a catalog, and `subagent-invoke`; `name=`
   and `resume=` support resumption, and three forgetting tiers manage context.
4. The agent topology is a tree; inject shares values across layers, and
   recovery proceeds along the tree.
