# v0.1.2 — 2026-10-04

## 中文

### `on_dequeue` 钩子消息级化

`on_dequeue` 的 value 类型由 `list[Message]` 改为单条 `Message`，触发时机从「回合启动批次构造完成」改为「每条消息的出队时点」，覆盖全部消费路径：回合启动批次的每条消息、回合内 INTERRUPT 吸收（连取 INTERRUPT + STEER 段）、回合内 STEER 吸收。`cancel_queued` 撤回与 `destroy` 整队放弃不是出队，不触发本钩子。

handler 可改写或丢弃该消息：

- **改写**：返回修改后的 `Message`，该消息（以改写后内容）照常挂树消费；返回消息的 `id` 与出队消息不同时，原消息视同丢弃（其等待者收 cancelled），返回消息为消费消息；
- **丢弃**：`raise flowing.errors.Intercepted`——消息不挂树、不落盘，其 `query()` 等待者联动收到
  `TurnResult(status="cancelled")`（框架合成空 `TurnContext`，与
  `cancel_queued` 同一填充规则）。丢弃一条 INTERRUPT 意味着本次中断
  不再触发回合 abort——这是契约允许的用法（仅当有 INTERRUPT 存活
  消息被吸收时才 abort；同段 STEER 存活则照常挂树进当轮 context）；
- **handler 普通异常**：被捕获并记录日志，该消息按丢弃处理（等待者
  cancelled），出队继续。

批次构造变成增量式：批次内逐条出队、逐条过钩子——这与旧行为不同
（旧实现中 dispatch 在整批构造完成后一次性发生，handler 入队的消息
不可能进入本批），是本次变更新增的可观察行为：钩子执行期间入队的
紧急消息可并入正在构造的批次；入队的普通消息可能被本批「首条非紧急」
位置提前消费。本批消息全部被丢弃时，工作循环重新等待下一批，不启动
空回合。

**不兼容性**：旧的批级 handler（按 `list[Message]` 处理、返回批次
列表、依赖「空批 = 丢弃重等」）不再适用，且不会报错只会行为异常。

**迁移**：批级变换（按来源分组、合并、整批过滤）迁移到
`before_turn`（改写 `turn.pending_messages`）或覆写
`Agent._dequeue`；单条过滤/改写直接改写现有 handler 的签名与返回
值即可。

**用法：** 消息级过滤与改写：

```python
def drop_spam(agent, msg):
    if msg.kind == MessageKind.USER and is_spam(msg):
        raise Intercepted    # 丢弃：不挂盘，query() 等待者收 cancelled
    return msg               # 改写：返回修改后的消息照常消费

agent.hooks.on_dequeue["spam_guard"](drop_spam, by="guard")
```

批重塑（回合启动粒度，整批视角）：

```python
def dedupe(agent, turn):
    seen = set()
    turn.pending_messages = [
        m for m in turn.pending_messages
        if not (m.id in seen or seen.add(m.id))
    ]
    return turn

agent.hooks.before_turn["dedupe"](dedupe, by="guard")
```

### `before_turn` 批重塑契约

`before_turn` 的可改写范围从「追加注入」扩展为完整的批次重塑：handler
可追加、移除或替换 `turn.pending_messages` 中的消息。三种操作的结局：

| 操作 | 消息去向 | 等待者结局 |
|---|---|---|
| 保留 / 追加 | 挂树进回合（照常触发 `on_turn_append`） | 共享本回合的 `TurnResult` |
| 移除 / 替换 | 不挂树、不落盘 | 随回合收尾收到本回合的 `TurnResult`（框架不做 cancelled 联动，善后由钩子作者负责） |
| `raise Intercepted` | 整批丢弃、不落盘 | `status="blocked"` |

回合内吸收的 INTERRUPT/STEER 消息不经过 `before_turn`（不存在回合
启动），批重塑不适用。

### 唯一出队接口 `Agent._dequeue_message`

新增内部 API `_dequeue_message(match)`：队首消息满足 `match` 则出队
单条并 dispatch `on_dequeue`（被丢弃的消息自动联动 cancelled，直至
拿到一条存活消息或队首不满足/队空返回 `None`）；不阻塞，等待归
`_dequeue` 的 `wait_not_empty`。核心全部出队路径（默认批次构造与回合内
urgent 吸收）经本接口出队；覆写 `_dequeue` 实现 drain/合并策略时，建议
逐条经本方法出队以保持 `on_dequeue` 覆盖（建议而非机制保证，见
`Agent._dequeue_message` docstring）。

### 新增 `Agent.count_context_messages()`

统计下一次 LLM 调用将看到的上下文消息数：沿 `current_head_id` 经
`MessageChain.walk` 上溯到根计数，与 `_assemble_context` 的消息路径
严格同口径（半截 turn 的已落盘消息照常计入、孤儿链断点容忍）。纯
观测实现——不拼接消息、不求值 prompt 段、不收集工具定义、不做配对
断言（`UnpairedToolCallError` 是装配时的不变量校验，计数不需要）、
无缓存，空路径返回 `0`。

**用法：** 应用层与 Composable 的策略判据（如自动压缩阈值）：

```python
if agent.count_context_messages() >= 200:
    ...   # 触发压缩 / 告警等策略动作
```

注意单位是消息条数，不是 token 数；token 口径用
`estimate_context_tokens()`。每次调用现场扫描 O(路径长)，结果随挂树 /
fork / 树手术即时变化。

### 修复：钩子异常不再终止消息工作循环

原实现中 `_dequeue` 调用位于 `_work_loop` 异常兜底（try 仅包
`_run_turn`）之外：`on_dequeue` handler 抛出的普通异常会沿
`_work_loop` 的 `while True` 向上传播，终止常驻消息工作循环 Task，
该 Agent 不再处理任何消息；且 `_dequeue` 已取出但尚未交付回合的
消息，其等待者留在 `_pending_turns` 中不被 resolve（直到
`destroy` 兜底）。现两处修复：`on_dequeue` handler 异常被捕获并
记录日志（该消息等待者 resolve cancelled、出队继续）；`_work_loop`
的 try 同时覆盖 `_dequeue` 调用，与回合异常同一兜底语义。

### 修复：Windows 上 record store 退出时被 poison

在 Windows 上退出 REPL（`/exit` 或 Ctrl+D）固定打印
`record store poisoned (...core.jsonl): [WinError 5] 拒绝访问`。根因：
原子重写（`_atomic_rewrite`）在常驻写句柄仍打开时就 `os.replace`
目标文件——POSIX 允许 rename 覆盖已打开的文件，Windows 的
`MoveFileEx` 拒绝。现重写在替换前关闭常驻句柄、替换后按原模式
惰性重建（`sync()` 重写后的续写依赖此），退出、墓碑压缩、版本迁移
回写路径在 Windows 上不再 poison。

同时修复关联挂死：墓碑压缩在 `close()` 的 drain 屏障分支失败
（poison 路径）时，已取出的 barrier 不被唤醒，`close()` 永久挂起；
现 barrier 唤醒置于 finally 兜底。

**用法：** 无需改动；Windows 上正常退出 REPL 即不再打印 poison。

## English

### `on_dequeue` hook is now message-level

The `on_dequeue` value changed from `list[Message]` to a single `Message`, and its timing moved from "after the turn-start batch is constructed" to "at each message's dequeue time", covering all consumption paths: every message of a turn-start batch, mid-turn INTERRUPT absorption (the INTERRUPT + STEER run), and mid-turn STEER absorption. `cancel_queued` retraction and whole-queue abandonment on `destroy` are not dequeues and do not fire this hook.

A handler may rewrite or drop the message:

- **Rewrite**: return the modified `Message`; it is appended and consumed as usual (with the rewritten content). If the returned message's `id` differs from the dequeued one, the original is treated as dropped (its waiter gets cancelled) and the returned message is the one consumed;
- **Drop**: `raise flowing.errors.Intercepted` — the message is not appended or persisted, and its `query()` waiter is resolved with `TurnResult(status="cancelled")` (a framework-synthesized empty `TurnContext`, same fill rule as `cancel_queued`). Dropping an INTERRUPT means this interruption no longer aborts the turn — a contract-sanctioned use (abort happens only when an INTERRUPT message survives absorption; surviving STEER messages in the same run are appended and visible to the current context as usual);
- **Ordinary handler exceptions** are caught and logged; the message is treated as dropped (waiter resolved cancelled) and dequeuing continues.

Batch construction becomes incremental: messages leave the queue one by one, each passing the hook — this differs from the old behavior (where dispatch happened once after the whole batch was constructed, so a message enqueued by a handler could never join the batch) and is a new observable behavior introduced by this change: urgent messages enqueued while a hook runs can join the batch under construction; a normal message enqueued in that window may be consumed early by the batch's "first non-urgent" slot. If every message of a batch is dropped, the work loop waits for the next batch instead of starting an empty turn.

**Incompatibility**: old batch-level handlers (treating the value as `list[Message]`, returning a batch list, relying on "empty batch = discard and re-wait") no longer apply and will misbehave silently instead of raising.

**Migration**: move batch-level transformation (grouping by source, merging, whole-batch filtering) into `before_turn` (rewriting `turn.pending_messages`) or an `Agent._dequeue` override; single-message filtering/rewriting only needs the existing handler's signature and return value updated.

**Usage:** message-level filtering and rewriting:

```python
def drop_spam(agent, msg):
    if msg.kind == MessageKind.USER and is_spam(msg):
        raise Intercepted    # drop: not persisted; the query() waiter gets cancelled
    return msg               # rewrite: the modified message is consumed as usual

agent.hooks.on_dequeue["spam_guard"](drop_spam, by="guard")
```

Batch reshaping (turn-start granularity, whole-batch view):

```python
def dedupe(agent, turn):
    seen = set()
    turn.pending_messages = [
        m for m in turn.pending_messages
        if not (m.id in seen or seen.add(m.id))
    ]
    return turn

agent.hooks.before_turn["dedupe"](dedupe, by="guard")
```

### `before_turn` batch-reshaping contract

`before_turn`'s writable scope extends from "append-style injection" to full batch reshaping: a handler may append, remove, or replace messages in `turn.pending_messages`. Outcomes per operation:

| Operation | Message fate | Waiter outcome |
|---|---|---|
| Keep / append | Appended to the turn (`on_turn_append` fires as usual) | Shares the turn's `TurnResult` |
| Remove / replace | Not appended, not persisted | Receives the turn's `TurnResult` at turn completion (no cancelled linkage; downstream cleanup is the hook author's responsibility) |
| `raise Intercepted` | Whole batch dropped, not persisted | `status="blocked"` |

Mid-turn absorbed INTERRUPT/STEER messages do not pass through `before_turn` (there is no turn start), so batch reshaping does not apply to them.

### Sole dequeue entry point: `Agent._dequeue_message`

New internal API `_dequeue_message(match)`: if the queue head matches `match`, dequeue one message and dispatch `on_dequeue` (dropped messages automatically resolve their waiters as cancelled, looping until a surviving message is obtained or the head no longer matches / the queue is empty, returning `None`). It does not block; waiting belongs to `_dequeue`'s `wait_not_empty`. All core dequeue paths (default batch construction and mid-turn urgent absorption) go through this entry point. When overriding `_dequeue` for drain/merge strategies, dequeue per message through this method to preserve `on_dequeue` coverage (a recommendation, not a mechanism guarantee — see the `Agent._dequeue_message` docstring).

### Added `Agent.count_context_messages()`

Counts the messages the next LLM call would see: walking from `current_head_id` to the root via `MessageChain.walk` — exactly the message path of `_assemble_context` (half-finished turn messages included; orphan breakpoints tolerated). Pure observation: no assembly, no prompt evaluation, no tool collection, no pairing assertion (`UnpairedToolCallError` is an assembly-time invariant check that counting does not need), no caching; an empty path returns `0`.

**Usage:** a policy input for the application layer and Composables (e.g. auto-compaction thresholds):

```python
if agent.count_context_messages() >= 200:
    ...   # trigger compaction / warnings / etc.
```

The unit is message count, not tokens; for the token view use `estimate_context_tokens()`. Each call scans on demand — O(path length) — and the result changes immediately with appends, forks, and tree edits.

### Fixed: hook exceptions no longer kill the message work loop

In the previous implementation the `_dequeue` call sat outside the `_work_loop` exception guard (the try wrapped only `_run_turn`): an ordinary exception from an `on_dequeue` handler propagated up the `_work_loop` `while True`, terminating the resident message work-loop Task, after which the Agent processed no further messages. Messages already dequeued but not yet delivered to a turn kept their waiters in `_pending_turns` unresolved (until the `destroy` fallback). Two fixes: `on_dequeue` handler exceptions are caught and logged (the message's waiter resolves as cancelled; dequeuing continues), and the `_work_loop` try now also covers the `_dequeue` call, with the same fallback semantics as turn exceptions.

### Fixed: record store poisoned on exit on Windows

Exiting the REPL on Windows (`/exit` or Ctrl+D) always printed
`record store poisoned (...core.jsonl): [WinError 5] Access is denied`.
Root cause: the atomic rewrite (`_atomic_rewrite`) replaced the target file
while the store's resident write handle was still open — POSIX allows
renaming over an open file, while Windows `MoveFileEx` refuses. The rewrite
now closes the resident handle before replacement and lazily reopens it in
the original mode afterwards (post-rewrite appends from `sync()` rely on
this); exit, tombstone compaction, and version-migration write-back no
longer poison the store on Windows.

A related hang is also fixed: when tombstone compaction fails inside
`close()`'s drain-barrier branch (the poison path), the already-dequeued
barrier was never woken and `close()` hung forever; the barrier wake-up now
sits in a `finally` as a backstop.

**Usage:** no changes needed; exiting the REPL on Windows no longer prints
the poison message.
